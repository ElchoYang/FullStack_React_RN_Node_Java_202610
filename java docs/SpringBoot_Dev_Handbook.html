手册使用说明

  • 写代码卡住 → 查第 2、3、4、6 章

第 2 章 核心注解与分层实现

2.1 注解速查

注解作用域用途备注
@Component类通用 Bean派生注解的父注解
@Service类业务层语义标注，无额外行为
@Repository类数据层会做持久层异常转换
@Controller / @RestController类Web 层后者 = 前者 + @ResponseBody
@Configuration类配置类内部 @Bean 方法被 CGLIB 代理
@Bean方法声明 Bean方法名即 Bean 名
@ConfigurationProperties类/方法批量绑定配置支持松散绑定、类型校验
@Value字段/参数单值注入不支持复杂类型与校验
@Profile类/方法按环境生效与 spring.profiles.active 联动
@ConditionalOnProperty类/方法按配置开关装配做可选能力时最常用
@Transactional类/方法事务详见 4.5 节失效场景
@Async方法异步执行需 @EnableAsync
@Scheduled方法定时任务需 @EnableScheduling
@Valid / @Validated参数/类参数校验 / 分组校验类上加 @Validated 才能校验方法参数
@RestControllerAdvice类全局异常 / 响应处理配合 @ExceptionHandler
@RequestMapping 家族类/方法路由映射见 6.1 节规范

2.2 依赖注入：只用构造器注入

java

@Service

public class OrderServiceImpl implements OrderService {

 

    private final OrderRepository orderRepository;

    private final PaymentClient paymentClient;

 

    // 单构造器可省略 @Autowired（Spring 4.3+）

    public OrderServiceImpl(OrderRepository orderRepository, PaymentClient paymentClient) {

        this.orderRepository = orderRepository;

        this.paymentClient = paymentClient;

    }

}

理由：字段注入（@Autowired 打在字段上）无法声明 final、无法脱离容器单测、循环依赖被隐藏。构造器注入让循环依赖在启动期直接报错，这是优点不是缺点。

同一类型多个 Bean 时：

java

@Service

public class PayService {

    private final Map<String, PayChannel> channels; // key = Bean 名

 

    public PayService(Map<String, PayChannel> channels) {

        this.channels = channels;

    }

}

按名注入优先级：@Primary > @Qualifier("name") > 字段名/参数名匹配。

2.4 全局异常处理

java

@RestControllerAdvice

@Slf4j

public class GlobalExceptionHandler {

 

    @ExceptionHandler(BizException.class)

    public ApiResponse<Void> handleBiz(BizException e) {

        log.warn("biz error: code={}, msg={}", e.getCode(), e.getMessage());

        return ApiResponse.fail(e.getCode(), e.getMessage());

    }

 

    @ExceptionHandler(MethodArgumentNotValidException.class)

    public ApiResponse<Void> handleValid(MethodArgumentNotValidException e) {

        String msg = e.getBindingResult().getFieldErrors().stream()

                .map(f -> f.getField() + ": " + f.getDefaultMessage())

                .collect(Collectors.joining("; "));

        return ApiResponse.fail(10001, msg);

    }

 

    @ExceptionHandler(Exception.class)

    public ApiResponse<Void> handleOther(Exception e) {

        log.error("unexpected error", e);          // 全堆栈只在此处打

        return ApiResponse.fail(50000, "系统繁忙，请稍后重试");

    }

}

三条纪律：① 对外永不移露堆栈与 SQL；② Exception 兜底必须 log.error 带堆栈；③ 业务异常用 warn 且不打堆栈，避免日志淹没。

自定义校验器（如手机号、枚举值）：

java

@Target({ElementType.FIELD})

@Retention(RetentionPolicy.RUNTIME)

@Constraint(validatedBy = PhoneValidator.class)

public @interface Phone {

    String message() default "手机号格式错误";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};

}

 

public class PhoneValidator implements ConstraintValidator<Phone, String> {

    private static final Pattern P = Pattern.compile("^1[3-9]\\d{9}$");

    @Override

    public boolean isValid(String v, ConstraintValidatorContext ctx) {

        return v == null || P.matcher(v).matches();  // null 交给 @NotBlank

    }

}

public static Specification<Order> build(OrderQuery q) {

    return (root, query, cb) -> {

        List<Predicate> ps = new ArrayList<>();

        if (q.getUserId() != null) {

            ps.add(cb.equal(root.get("userId"), q.getUserId()));

        }

        if (q.getStatus() != null) {

            ps.add(cb.equal(root.get("status"), q.getStatus()));

        }

        if (q.getFrom() != null) {

            ps.add(cb.greaterThanOrEqualTo(root.get("createdAt"), q.getFrom()));

        }

        return cb.and(ps.toArray(new Predicate[0]));

    };

}

4.4 解决 N+1 与 open-in-view

N+1 表现：查 1 条主表 + N 条子表，日志里冒出几百条 SQL。

三种解法，按推荐顺序：

  1. 需要什么查什么：列表页只查主表，子信息用单独的批量查询（findByOrderIdIn(ids)）组装成 VO。
  2. @EntityGraph 或 join fetch：一次 join 拿全。
  3. hibernate.default_batch_fetch_size: 100：把 N 次查询压成少数几次 in 查询。
java

@EntityGraph(attributePaths = {"items"})

List<Order> findWithItemsByUserId(Long userId);

spring.jpa.open-in-view 默认是 true，会把 EntityManager 的打开范围拉到整个请求周期，导致：① 掩盖懒加载设计问题；② 连接被长时间持有；③ 事务外仍能发 SQL 但无事务保障。生产必须设为 false，关了之后报 LazyInitializationException 是正常的 —— 说明该在 Service 内取的数据没取。

传播行为速查：

传播行为行为场景
REQUIRED（默认）有则加入，无则新建绝大多数业务
REQUIRES_NEW挂起外层，独立新事务记录审计日志（外层回滚也要留）
NESTED保存点，可局部回滚批量导入中单条失败不影响整批
SUPPORTS有则用，无则非事务查询方法
NOT_SUPPORTED挂起外层，非事务执行事务中调外部慢接口
MANDATORY必须已有事务强制要求上层开事务
NEVER不能有事务—

5.3 索引设计

原则：

  1. 单表索引 ≤ 5 个，每个索引都要有明确查询场景支撑。
  2. 联合索引遵循最左前缀，把区分度高的列放左边（user_id, created_at 优于 created_at, user_id）。
  3. 区分度低的列（性别、状态）不单独建索引，可作联合索引的末位。
  4. 更新频繁的列慎建索引。
  5. 长字符串用前缀索引：index idx_name (name(20))。
sql

-- 覆盖索引：查询列全在索引里，避免回表

ALTER TABLE t_order ADD INDEX idx_user_status_created (user_id, status, created_at);

 

-- 唯一索引

ALTER TABLE t_order ADD UNIQUE INDEX uk_order_no (order_no);

 

-- 查看索引使用情况（MySQL 8）

SELECT * FROM sys.schema_unused_indexes WHERE object_schema = 'demo';

索引失效场景（背下来）：

场景示例说明
函数/运算包裹列where date(created_at) = '2026-01-01'改成范围查询
隐式类型转换where phone = 13800000000（列是 varchar）加引号
前导模糊like '%abc'改 like 'abc%' 或全文索引
or 混用无索引列where a = 1 or b = 2拆成两次查询 union
违反最左前缀索引 (a,b)，查 where b = 1补全 a 或另建索引
!= / not in / is not null大范围取反区分度低时全表扫
排序字段与索引顺序不一致order by b，索引 (a,b)调整索引或排序

sql

-- 分页（深分页优化：用游标而非 offset）

-- 差：select * from t_order order by id limit 1000000, 20;

SELECT * FROM (

WITH RECURSIVE dept_tree AS (

  SELECT id, parent_id, name FROM t_dept WHERE id = 1

10.2 JWT 过滤链

text

请求 → JwtAuthFilter（解析 Header 里的 Bearer Token）

     → 校验签名/过期 → 构造 Authentication 放入 SecurityContextHolder

     → SecurityFilterChain 授权判断 → Controller

java

@Component

public class JwtAuthFilter extends OncePerRequestFilter {

 

    private final JwtUtil jwtUtil;

 

    public JwtAuthFilter(JwtUtil jwtUtil) { this.jwtUtil = jwtUtil; }

 

    @Override

    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,

                                    FilterChain chain) throws ServletException, IOException {

        String h = req.getHeader(HttpHeaders.AUTHORIZATION);

        if (h != null && h.startsWith("Bearer ")) {

            try {

                Claims c = jwtUtil.parse(h.substring(7));

                var auth = new UsernamePasswordAuthenticationToken(

                        c.getSubject(), null,

                        List.of(new SimpleGrantedAuthority("ROLE_" + c.get("role"))));

                SecurityContextHolder.getContext().setAuthentication(auth);

            } catch (JwtException e) {

                SecurityContextHolder.clearContext();   // 过期/伪造：不抛异常，交给入口点返回 401

            }

        }

        chain.doFilter(req, res);

    }

}

要点：过滤器里不要直接写 401 响应，清空上下文让 authenticationEntryPoint 统一处理，避免响应格式不一致。

附录 B 从 3.x 升级到 4.x 的检查清单

Spring Boot 4.0 是一次代际升级，破坏性改动集中在这几块：

变更影响应对
基线 Spring Framework 7 / Jakarta EE 11传递依赖整体抬升（Hibernate 7、Tomcat 11、Security 7、Jackson 3）先升到 3.5，清空弃用告警，再跨 4.x
自动配置模块化拆分依赖 spring-boot-autoconfigure 内部类的自研 starter 编译失败改按具体模块依赖，只用公开扩展点
JSpecify 空安全注解IDE 出现大量可空性告警按告警逐项修，重点是入参校验
部分配置项重命名旧 key 失效但不报错用 spring-boot-properties-migrator 跑一遍，看启动日志提示
声明式 HTTP 客户端RestTemplate 不再自动配置改用 RestClient 或 @HttpExchange 接口
Jackson 3JSON 序列化默认行为变化回归日期格式、null 处理、多态类型
虚拟线程开启后 synchronized 阻塞会 pin 线程换 ReentrantLock，压测验证

升级步骤：

text

1. 升到 3.5 最新补丁，删掉所有弃用 API 调用

2. 引入 spring-boot-properties-migrator，跑起来看配置重命名提示

3. 改 parent 版本到 4.x，mvn -U clean compile，逐个修编译错误

4. 跑全量测试；重点回归安全配置、JSON 序列化、数据访问

5. 预发压测，对比 P99 与内存占用
