一、Spring 与 Spring Boot：先厘清关系

本章先厘清 Spring 与 Spring Boot 的关系，为后续核心概念回顾建立全局视角。

（一）一句话定位

  • Spring Framework：Java 企业级开发的基础框架，核心是 IoC 容器与 AOP，外加事务、MVC、数据访问等模块。

  • Spring Boot：不是替代 Spring，而是简化 Spring 的脚手架——自动配置、起步依赖（Starter）、内嵌服务器，让你"开箱即用"。

（二）Spring Boot 项目最小骨架

// src/main/java/com/example/demo/DemoApplication.java

二、IoC 控制反转与 DI 依赖注入

IoC 是整个 Spring 体系的基石，本章从概念、动机、注入方式到生命周期做一次系统回顾。

（一）核心概念：什么是控制反转

  • IoC（Inversion of Control，控制反转）：对象的创建和依赖组装权从程序员手里反转给容器。你不再 new UserService()，而是声明"我需要一个 UserService"，容器负责造好并递给你。

  • DI（Dependency Injection，依赖注入）：IoC 的主要实现方式——容器在创建对象时，把它依赖的其他对象注入进来。

  • Bean：由 Spring 容器创建和管理的对象实例。

一句话记忆：IoC 是思想，DI 是手段，Bean 是结果。

（二）为什么要控制反转

不使用 IoC 的传统写法：

public class OrderController {
    // 强耦合：自己 new，换实现必须改代码
    private OrderService orderService = new OrderServiceImpl();
}

使用 IoC 之后：

@Service                          // 声明为 Bean，交给容器管理
public class OrderServiceImpl implements OrderService { ... }

@RestController
public class OrderController {
    private final OrderService orderService;

    // 构造器注入：容器自动把 OrderServiceImpl 实例传进来
    public OrderController(OrderService orderService) {   // 只依赖接口
        this.orderService = orderService;
    }
}

收益：

  • 解耦：面向接口编程，替换实现只需换一个 Bean，不改调用方代码。

  • 可测试：单元测试时注入 Mock 对象即可。

  • 统一生命周期管理：容器负责创建、初始化、销毁，支持 AOP 增强。

（五）依赖注入的匹配规则

同一接口有多个实现时，需要消歧：

public interface PayService { void pay(); }

@Service("aliPay")
public class AliPayService implements PayService { ... }

@Service("wechatPay")
public class WechatPayService implements PayService { ... }

三种消歧方式：

// 1. @Qualifier 按名称指定
public OrderService(@Qualifier("aliPay") PayService payService) { ... }

// 2. @Primary 在某个实现上标记"默认首选"
@Service @Primary
public class AliPayService implements PayService { ... }

// 3. 注入整个集合，运行时按条件选择
public OrderService(List<PayService> payServices) { ... }

（七）Bean 生命周期回顾要点

实例化 → 属性注入 → Aware 回调 → BeanPostProcessor 前置处理
       → @PostConstruct / InitializingBean → 定制 init-method
       → Bean 就绪可用
       → 容器关闭 → @PreDestroy / DisposableBean → 定制 destroy-method
@Component
public class CacheWarmer {
    @PostConstruct                  // 依赖注入完成后执行，做初始化
    public void warmUp() { System.out.println("缓存预热完成"); }

    @PreDestroy                     // 容器关闭前执行，做资源释放
    public void shutdown() { System.out.println("释放缓存资源"); }
}
注意：singleton Bean 从启动即存在，不要在 singleton 中持有可变共享状态；prototype Bean 的销毁回调不由容器自动触发。

三、AOP 面向切面编程

AOP 解决的是横切关注点的复用问题，本章覆盖术语、通知类型、切入点写法与实现原理。

（一）为什么需要 AOP

AOP（Aspect-Oriented Programming，面向切面编程）把"日志、事务、权限、缓存"这类横切关注点（散布在众多业务方法里的通用逻辑）从业务代码中抽离出来，集中到一个"切面"里统一维护，运行时由框架动态织入。

没有 AOP：每个 Service 方法都要手写一遍"记日志 → 开事务 → try 业务 → 提交/回滚"。有 AOP：业务方法只写业务，横切逻辑由切面统一接管。

（二）核心术语速查

表 3-1 AOP 核心术语
术语英文一句话解释

表 3-2 五种通知类型
通知类型注解执行时机典型用途

（四）完整示例：接口耗时监控切面

// build.gradle 需引入：implementation 'org.springframework.boot:spring-boot-starter-aop'

@Aspect                       // 声明这是一个切面
@Component                    // 切面本身也要交给容器管理
public class PerformanceAspect {

    // 切入点：service 包下所有类的所有方法
    @Pointcut("execution(* com.example.demo.service..*.*(..))")
    public void serviceLayer() {}

    // 环绕通知：可以控制目标方法是否执行、何时执行
    @Around("serviceLayer()")
    public Object timeit(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();                        // 执行目标方法
        } finally {
            long cost = System.currentTimeMillis() - start;
            System.out.println(pjp.getSignature() + " 耗时 " + cost + "ms");
        }
    }
}

预期输出：

void com.example.demo.service.OrderServiceImpl.createOrder(Order) 耗时 37ms

（六）实现原理：JDK 动态代理与 CGLIB

表 3-4 两种动态代理对比
对比项JDK 动态代理CGLIB
原理基于接口，反射生成代理类基于继承，字节码生成子类

四、ORM 与数据访问

数据访问层围绕 ORM 展开，本章对比三大主流方案并给出快速上手示例与事务要点。

（一）ORM 是什么

ORM（Object-Relational Mapping，对象关系映射）把 Java 对象和数据库表互相映射：操作对象就等于操作表，屏蔽手写 SQL 与 JDBC 样板代码。

Java 生态数据访问技术演进：

原生 JDBC（样板代码地狱）
  → JdbcTemplate（Spring 封装，消除样板）
    → MyBatis（SQL 映射框架，SQL 自己写、映射自动做）
    → JPA / Hibernate（全自动 ORM，连 SQL 都帮你生成）
      → Spring Data JPA（JPA 之上的仓库抽象，方法名即查询）

（二）三大方案对比

表 4-1 JdbcTemplate / MyBatis / Spring Data JPA 对比
对比项JdbcTemplateMyBatisSpring Data JPA
SQL 控制权全手写全手写框架生成，可覆写
开发效率低中高
学习成本低中中偏高

选型现状：国内互联网公司偏 MyBatis（SQL 可控）；海外与领域驱动项目偏 JPA。两者可共存于同一项目。

（三）JPA 快速上手

依赖与配置：

// build.gradle
implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
runtimeOnly   'com.mysql:mysql-connector-j'
# src/main/resources/application.yml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/demo?useSSL=false&serverTimezone=Asia/Shanghai
    username: root
    password: secret
  jpa:
    hibernate:
      ddl-auto: update      # 开发期方便，生产环境必须改为 none 或由 Flyway 管理
    show-sql: true

实体与仓库：

// src/main/java/com/example/demo/entity/User.java
@Entity
@Table(name = "t_user")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // 主键自增
    private Long id;

    private String name;

    @Column(nullable = false, unique = true)
    private String email;
    // getter / setter 省略
}
// src/main/java/com/example/demo/repository/UserRepository.java
public interface UserRepository extends JpaRepository<User, Long> {
    // 方法名即查询：框架自动解析生成 SQL
    List<User> findByNameContaining(String keyword);

    // 复杂查询用 @Query
    @Query("select u from User u where u.email like %:domain%")
    List<User> findByEmailDomain(@Param("domain") String domain);
}

使用：

@Service
@RequiredArgsConstructor
public class UserService {
    private final UserRepository userRepository;

    public User create(String name, String email) {
        return userRepository.save(new User(name, email));   // 新增或更新
    }

    public List<User> search(String keyword) {
        return userRepository.findByNameContaining(keyword); // 预期输出：匹配用户列表
    }
}

（四）MyBatis 快速上手（Spring Boot 3）

// build.gradle
implementation 'org.mybatis.spring.boot:mybatis-spring-boot-starter:3.0.3'
// src/main/java/com/example/demo/mapper/UserMapper.java
@Mapper                                   // 声明 MyBatis 映射接口
public interface UserMapper {
    @Select("select * from t_user where id = #{id}")
    User findById(Long id);

    @Insert("insert into t_user(name, email) values(#{name}, #{email})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(User user);
}
注解方式适合简单 SQL；SQL 复杂、需要动态拼接时改用 XML 映射文件（resources/mapper/*.xml），配合 if、foreach 等动态标签。

（五）声明式事务：@Transactional

@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;
    private final StockRepository stockRepository;

    @Transactional                        // 方法内所有 DB 操作包在一个事务里
    public void createOrder(Order order) {
        orderRepository.save(order);      // 任意一步抛 RuntimeException
        stockRepository.deduct(order);    // 整体回滚，不会出现半下单
    }
}

  踩坑 1：自调用失效——同类中 this.createOrder() 不经过代理，事务不生效（与 AOP 同源问题）。

  踩坑 2：默认只回滚 RuntimeException 和 Error——受检异常需写 @Transactional(rollbackFor = Exception.class)。

  踩坑 3：方法必须 public——非 public 方法上的 @Transactional 静默失效。

  踩坑 4：传播行为——REQUIRED（默认，加入当前事务）、REQUIRES_NEW（挂起外层另开新事务）、NESTED（嵌套保存点）是最常用的三种。

七、常见问题 FAQ

Q1：IoC 和 DI 是一回事吗？

不是。IoC 是设计思想（控制权反转），DI 是实现该思想的主要手段（依赖注入）。常混用，但面试要能区分。

Q2：@Autowired 和 @Resource 有什么区别？

@Autowired 是 Spring 提供，默认按类型匹配，配合 @Qualifier 按名称；@Resource 是 JSR-250 标准注解，默认按名称匹配，找不到再按类型。

Q3：为什么我的 AOP 切面 / @Transactional 不生效？

九成是自调用问题：同一个类内部 this.method() 不走代理。其余检查：方法是否 public、类是否被容器管理、异常是否被 catch 吞掉。

Q4：MyBatis 和 JPA 该选哪个？

SQL 密集、经常写复杂查询和报表 → MyBatis；领域模型清晰、以 CRUD 为主、追求开发效率 → JPA。两者不互斥。

Q5：ddl-auto 为什么生产环境不能用 update？

update 会自动改表结构，存在字段丢失/锁表风险。生产应设为 none，用 Flyway/Liquibase 管理数据库变更脚本。

Q6：循环依赖怎么解决？

首选重新设计依赖方向；其次用 @Lazy 延迟注入其中一方；构造器注入的循环依赖 Spring Boot 2.6+ 默认直接启动失败，这是刻意设计。

  • 巩固基础：手写一个简化版 IoC 容器（理解 BeanDefinition、反射创建、依赖组装）。

  • 源码阅读：从 AbstractApplicationContext.refresh() 入手，理解容器刷新全流程；再看 BeanPostProcessor 如何织入 AOP 代理。

  • Web 进阶：Spring MVC 请求处理流程、全局异常处理（@ControllerAdvice）、参数校验（@Validated）。

  • 数据进阶：多数据源配置、读写分离、MyBatis-Plus / Spring Data JDBC。

  • 生产实践：Actuator 监控、日志规范、Flyway 数据库迁移、Docker 部署。
